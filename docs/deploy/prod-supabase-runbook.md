# PROD Supabase stack runbook (#1115)

- Issue: #1115, part of the PROD series (#1113 to #1120)
- Related: [ADR 0002](../decisions/0002-backend-hosting-on-dokploy.md) and its 2026-11-16 amendment, [ADR 0004](../decisions/0004-sign-in-with-google-microsoft-and-email-code.md), [`deploy/README.md`](../../deploy/README.md), [step 0 report (#1113)](prod-step0-readonly-checks.md)

**Who runs this: Mario, by hand, in the Dokploy, Google Cloud, Resend and EAS interfaces.** An agent only writes this document. It contains no secret values, IP addresses or account identifiers, and it must stay that way: put every value in the interface named in each step, never in the repository, a chat or a ticket.

## What this runbook builds

An empty Supabase stack for PROD, in its own Dokploy project, with secrets of its own. At the end of this runbook the stack is healthy and configured, but it has:

- no public route yet (the Dokploy domain and the Cloudflare tunnel rule are #1116),
- no migrations and no PowerSync (the `deploy/compose.yaml` deploy is #1116),
- no Edge Functions and no function-level `pg_cron` work (#1117),
- no school administrator (#1118) and no backups (#1119).

Do not do any of those here. Do not copy any data from QA.

## Requirements that never change

These three are requirements, not preferences. If one of them is not true, PROD is not ready:

| Requirement | Where it is set |
| --- | --- |
| `APPLY_SEED=false`, for ever. PROD never gets the demo data. | The `deploy` compose environment in the PROD project (set in #1116; this runbook only checks it, step 7). |
| `FUNCTIONS_VERIFY_JWT=true` | The Supabase stack environment (step 6). |
| Microsoft sign-in is **off** until Mario confirms it. | The Supabase stack environment (step 5). |

## Secrets: where each one goes and which are unique

Every secret is created for PROD and **never has the same value as in QA**. Nothing is copied from the QA stack, not even "temporarily". The Dokploy Supabase template generates many of its own secrets when the application is created: keep those and never paste a QA value over them.

| Secret | Where Mario puts it | Unique per environment |
| --- | --- | --- |
| JWT secret (`JWT_SECRET` in the Supabase stack) | Dokploy, environment of the PROD Supabase stack. The same value goes later into `SUPABASE_JWT_SECRET` of the PROD `deploy` compose (#1116). | Yes |
| Anon key (`ANON_KEY`) and service role key (`SERVICE_ROLE_KEY`) | Dokploy, same environment. Both are tokens signed with the JWT secret: they must come from PROD's secret, so if the JWT secret is replaced they are generated again. The anon key is public and goes to EAS as `EXPO_PUBLIC_SUPABASE_ANON_KEY` at the cut (#1120). The service role key never leaves the server. | Yes |
| Database password (`POSTGRES_PASSWORD` in the stack; `SUPABASE_DB_PASSWORD` in the `deploy` compose) | Dokploy: the stack environment, and later the `deploy` compose environment with the same value | Yes |
| `POWERSYNC_DB_PASSWORD` | Dokploy, `deploy` compose environment (#1116) | Yes |
| `POWERSYNC_STORAGE_PASSWORD` | Dokploy, `deploy` compose environment (#1116) | Yes |
| Other secrets the template generates (internal keys, dashboard credentials) | Dokploy, generated by the template for PROD | Yes: never overwrite them with QA values |
| `athlete_identity_key` | Supabase Vault of the PROD database (step 6), with a copy in the team's password manager | Yes. Losing it makes the stored identity numbers unreadable. |
| SMTP credentials (Resend) | Dokploy, stack environment (step 4). Recommended: an API key made only for PROD, so it can be revoked without touching QA. | Recommended. The sender and the verified domain are QA's. |
| Google OAuth client ID and secret | Created in Google Cloud, then set in Dokploy, stack environment (step 5) | Yes: a client made for PROD |

The three passwords go inside connection URIs in the `deploy` compose, so they must be URL-safe: letters and digits only (for example the output of `openssl rand -hex 24`). Generate them on your side and put them directly in Dokploy and in the team's password manager.

## Steps

Mark each box when it is done. Do the steps in order: step 2 fixes the hostnames that the values of steps 4 to 6 refer to.

### 0. Before anything

- [ ] The [step 0 report (#1113)](prod-step0-readonly-checks.md) is merged, and you authorized building PROD on the same server (decision Q6, 2026-11-16, in that report).
- [ ] You have access to Dokploy, Google Cloud (the project that owns the Swimcro OAuth consent screen) and Resend.

### 1. Create the Dokploy project «Swimcro PROD»

On the same Dokploy server as QA.

- [ ] Create a project named «Swimcro PROD». It is separate from the QA project `TrailSkill`: PROD and QA never share a project, a network or a compose.
- [ ] Remember the capacity rule from the step 0 report: the PROD stack fits at the ADR 0002 minimum (4 GB of RAM, about 5.7 GB free after it) with little margin. If memory runs short, the fix is a limit on QA (planned in #1116), not a smaller PROD.

### 2. Create the Supabase application from the template

- [ ] In «Swimcro PROD», create a Supabase application from the Dokploy Supabase template, the same template and version QA was built from.
- [ ] **Delete the template's default public domain** (the `sslip.io` one). The PROD stack has no public domain of its own.
- [ ] The only public hostnames PROD will ever have are `swimcro-api.tuls.app` (the API gateway, port 8000) and `swimcro-sync.tuls.app` (PowerSync, port 8080). Adding them as Dokploy domains and the Cloudflare route are #1116: **publish nothing in this runbook.**
- [ ] Set the three variables that carry the public API address, all to `https://swimcro-api.tuls.app`: `SUPABASE_PUBLIC_URL`, `API_EXTERNAL_URL` (also the JWT issuer) and `SITE_URL`. They are plain addresses, not secrets. A wrong value makes every token invalid later: check them again before #1116.
- [ ] Do **not** publish Studio. Do **not** add Mailpit (it exists only in QA).
- [ ] Write down the application's **app name**. The Docker network of the stack is `<app name>_default` and the `deploy` compose needs it as `SUPABASE_NETWORK` (#1116). The database host on that network is the database container, `<app name>-db-1`: use it as `SUPABASE_DB_HOST` in #1116, never `db` (see the [collision report](prod-deploy-compose.md#a-collision-report-two-copies-of-deploycomposeyaml-on-one-server)).

### 3. `pg_cron`

The two daily family-timing jobs run inside the database through `pg_cron` ([Scheduled jobs](../../deploy/README.md#scheduled-jobs-pg_cron)). Every `migrate` run registers them, but only if the extension is installed first. PROD starts empty, so install it now, before the first deploy.

- [ ] Open a SQL session as a role that can create extensions: `psql` as `postgres` inside the server, or the SQL editor of Studio reached internally (never published).
- [ ] Check that the extension is available and preloaded:

  ```sql
  select name, installed_version from pg_available_extensions where name = 'pg_cron';
  show shared_preload_libraries;
  show cron.database_name;
  ```

- [ ] `pg_cron` must be in `shared_preload_libraries` and `cron.database_name` must be the app database (`postgres`). If not, add `pg_cron` to `shared_preload_libraries` in the database service of the PROD stack in Dokploy and restart the database. The stack is empty, so there is no outage to plan.
- [ ] Install it in the app database:

  ```sql
  create extension if not exists pg_cron;
  ```

- [ ] In #1116, the first `migrate` log must say `scheduled jobs: 2`. `scheduled jobs: 0` or `WARN scheduled jobs failed` means this step was skipped or the role cannot use `cron.schedule`: follow the [maintainer checklist](../../deploy/README.md#scheduled-jobs-pg_cron).

#### Account deletion worker (#1244)

The daily account deletion worker is a third `pg_cron` job (`accounts-deletion-worker`, 04:37 UTC). It runs `app.call_accounts_deletion_worker()`, which posts to the `accounts-deletion-worker` Edge Function through `pg_net`. Accounts marked for deletion that reach day 30 stay marked and blocked until it runs. #1233 (the Storage queue worker) must use this same `pg_cron` → `pg_net` → Edge Function route so only one scheduled worker exists.

- [ ] Install `pg_net` next to `pg_cron`: `create extension if not exists pg_net;`. Without it, or without `pg_cron`, the next `migrate` run schedules nothing and the deploy does not fail.
- [ ] Choose a long random value for the worker secret (`openssl rand -hex 32`). Set it as `ACCOUNTS_WORKER_SECRET` in the environment of the functions service, and store the same value in Vault together with the function URL (the URL of `accounts-deletion-worker` as the database reaches it, for example `http://kong:8000/functions/v1/accounts-deletion-worker`):

  ```sql
  select vault.create_secret('<the function url>', 'accounts_worker_url');
  select vault.create_secret('<the same value as ACCOUNTS_WORKER_SECRET>', 'accounts_worker_secret');
  ```

  Until both secrets exist, the call logs `accounts deletion worker is not configured` and does nothing.
- [ ] The functions service also needs `RESEND_API_KEY` and `RESEND_FROM` (the same as `school-console-invite-coach`). Without them the worker deletes on day 30 but the emails stay unsent and are retried on every run.
- [ ] The functions bundle (`deploy/scripts/functions-bundle.sh`, `FUNCTIONS`) must list `accounts-delete-account` and `accounts-deletion-worker`, and both import the Resend sender from `school-console-invite-coach`. This PR does not touch `deploy/`; the maintainer adds them.
- [ ] After the next `migrate` run, `select jobname, schedule from cron.job where jobname = 'accounts-deletion-worker';` returns one row.

### 4. Email: SMTP with Resend

Auth sends the sign-in code through Resend over SMTP, with the sender `Swimcro <no-reply@send.tuls.app>` (ADR 0002 amendment).

- [ ] **First, before any new DNS record: Mario confirms which sending domain is already verified in Resend.** If `send.tuls.app` is verified, PROD reuses it and no DNS record is created. If another domain is the verified one, or none is, stop and tell the maintainer; do not create records on your own.
- [ ] In Resend, create an API key used only by PROD (recommended, see the secrets table).
- [ ] In the PROD stack environment in Dokploy, set the template's SMTP variables (host, port, user and password: the same variables QA's stack uses for Resend) and the sender `Swimcro <no-reply@send.tuls.app>`. The values come from Resend and are not written in the repository.
- [ ] Set `ENABLE_EMAIL_AUTOCONFIRM=false`, `ENABLE_PHONE_SIGNUP=false` and `ENABLE_ANONYMOUS_USERS=false`.
- [ ] The code email. Make the PROD Auth service send the 6-digit code with the `otp.html` template exactly as QA does, described in [`deploy/README.md`](../../deploy/README.md#one-time-setup-in-dokploy): the internal `mail-templates` service (no domain) with the `otp.html` file mount that contains `{{ .Token }}`, the variables `GOTRUE_MAILER_TEMPLATES_MAGIC_LINK` and `GOTRUE_MAILER_TEMPLATES_CONFIRMATION` (`http://mail-templates:8080/otp.html`), and `GOTRUE_MAILER_SUBJECTS_MAGIC_LINK` and `GOTRUE_MAILER_SUBJECTS_CONFIRMATION` (`Tu código de Swimcro`). Leave `GOTRUE_MAILER_OTP_LENGTH` unset (default 6).
- [ ] Do not point SMTP at Mailpit. PROD has no Mailpit.

### 5. GoTrue: Google and the email code

Sign-in in PROD is Google and the email code. No passwords (ADR 0004).

- [ ] **Microsoft is off.** In the PROD stack environment the Microsoft provider (`GOTRUE_EXTERNAL_AZURE_ENABLED`) is `false`, with no client ID or secret. It stays off until Mario confirms it; turning it on is a new decision, not part of this runbook.
- [ ] **Google, a client made for PROD.** In Google Cloud, create a new **web** OAuth client; do not reuse QA's:
  - Authorized redirect URI: `https://swimcro-api.tuls.app/auth/v1/callback`, the only one.
  - The consent screen asks for the basic email and profile scopes only. If it is still in **Testing**, only the listed test users can sign in: decide with the maintainer whether to list the testers or publish it before real families are invited.
  - In the PROD stack environment set `GOTRUE_EXTERNAL_GOOGLE_ENABLED=true`, `GOTRUE_EXTERNAL_GOOGLE_CLIENT_ID`, `GOTRUE_EXTERNAL_GOOGLE_SECRET` and `GOTRUE_EXTERNAL_GOOGLE_REDIRECT_URI` (the callback above).
- [ ] **Redirect URLs.** `ADDITIONAL_REDIRECT_URLS` has exactly one entry: `swimcro://auth-callback`. Not `trailskill://auth-callback` (builds from before the rename never reach PROD) and not `swimcro-preview://auth-callback` (the preview APK stays on QA). Without the entry GoTrue falls back to `SITE_URL` and the browser ends on that page instead of returning to the app.
- [ ] Redeploy the Auth service so it reads the new variables. Testing a real sign-in needs the public route, so it belongs to #1116 and the smoke test of #1120.

### 6. Secrets of the stack: keys, passwords and Vault

- [ ] **JWT secret, anon key and service role key** are PROD's own and consistent with each other (see the secrets table). Check that they differ from QA's without copying either set anywhere: both live only in Dokploy.
- [ ] **`FUNCTIONS_VERIFY_JWT=true`** in the PROD stack environment (the `functions` service reads it as `VERIFY_JWT`). It is `true` from the first deploy, so the runtime rejects requests without a valid JWT before they reach any function.
- [ ] **Database password**: the stack's own, not shared with QA. In #1116 the `deploy` compose takes the same value as `SUPABASE_DB_PASSWORD`.
- [ ] **PowerSync passwords**: choose `POWERSYNC_DB_PASSWORD` and `POWERSYNC_STORAGE_PASSWORD` for PROD, URL-safe, different from QA's and from each other. Store them in the team's password manager now; they are set in Dokploy in #1116.
- [ ] **Vault key `athlete_identity_key`, before the first migration of #1116.** The identity-number migration needs it ([Identity number key](../../deploy/README.md#identity-number-key-vault)). In the same privileged SQL session as step 3:

  ```sql
  select vault.create_secret('<output of: openssl rand -base64 32>', 'athlete_identity_key');
  ```

  Generate the value with `openssl rand -base64 32` on your side and keep a copy in the team's password manager. It is not QA's key.

### 7. `APPLY_SEED=false` for ever

- [ ] Nothing to set in the Supabase stack: `APPLY_SEED` is a variable of the `deploy` compose (#1116), whose default in `deploy/compose.yaml` is already `false`. The requirement is that it **stays `false` for ever**: PROD never applies `supabase/seed.sql`, and the demo accounts must never exist there. Check it again after every change to the PROD `deploy` compose.

### 8. Exit checks (read only)

Nothing here changes anything. Do it when steps 1 to 7 are done:

- [ ] **Services healthy.** In Dokploy, every service of the PROD stack is running and healthy (database, Auth, API gateway, Realtime, Storage, Functions and the rest of the template). Read the Auth logs for SMTP or Google configuration errors only.
- [ ] **No Mailpit, no Studio published.** The PROD project has no `mailpit` service, and neither Studio nor any other service has a domain. At this point the project has no domain at all: the two routes come in #1116.
- [ ] **No secrets in the repository.** On a clone of the repository run:

  ```sh
  git grep -nE '(eyJ[A-Za-z0-9_-]{20,}\.[A-Za-z0-9_-]{20,}\.|GOCSPX-|re_[A-Za-z0-9]{20,}|BEGIN (RSA |EC )?PRIVATE KEY)' -- ':!*.lock'
  ```

  Every hit must be a test fixture or a placeholder you can name. A hit you cannot explain is a leaked secret: tell the maintainer before doing anything else.
- [ ] **Different from QA.** The JWT secret, the anon key, the database password and the Google client of PROD are not QA's. Compare without printing the values.
- [ ] **Capacity.** Note the server's free RAM and free disk as the starting point. Proposed thresholds, **not decided; Mario confirms**: investigate when free RAM falls below 3 GB or disk use goes above 85 %.
