# Play Data safety form: proposed answers (BORRADOR)

> **BORRADOR.** Proposed answers for the Data safety section of Play Console, derived from what the app stores today. They are not legal advice and are not final: the maintainer confirms each answer, and the legal review of issue #106 validates them together with the privacy policy ([`privacy-policy.es.md`](privacy-policy.es.md)). Play requires the form to stay accurate, so update it whenever the collected data changes ([`docs/RELEASING.md`](../RELEASING.md#google-play)). Contains no real names of schools, federations, or people.

Evidence is the repository at the time of writing: `supabase/migrations/` (tables), `powersync/sync-config.yaml` (what syncs to a device), `src/modules/*` (what each screen collects) and `src/core/*`. Re-check it against the code before submitting.

## What the app collects

Everything is entered by the user or captured by the timing screens. There is no advertising, analytics, or crash-reporting SDK in `package.json`, no location, camera, microphone, contacts, or storage permission, and no code that reads the device advertising ID.

| Data | Whose | Where it is stored | Module / source |
| --- | --- | --- | --- |
| Email address | Every signed-in user | Supabase Auth (`auth.users`) | `src/core/session/SessionProvider.tsx` (`signInWithOtp`, `verifyOtp`, `signInWithOAuth`) |
| User ID | Every signed-in user | `auth.users.id`, referenced as `created_by`, `user_id`, `confirmed_by`, `requested_by` in many tables | all modules |
| First and last name of an adult account | Guardian or adult athlete | `adult_profiles` (`20261025110000_accounts_adult_profiles.sql`) | `src/modules/accounts` |
| First and last name of an athlete | Athlete (may be a minor) | `athletes` (`20261024200100_athletes_athletes.sql`) | `src/modules/accounts`, `src/modules/athletes` |
| Identity document number of an athlete | Athlete | `athlete_identity_documents.identity_number_encrypted`, encrypted, no direct read access for the app roles (`20261028223000_accounts_athlete_identity_documents.sql`) | `src/modules/accounts` |
| Who manages an athlete, school membership, group and category | Athlete, guardian, staff | `athlete_managers`, `athlete_schools`, `athlete_groups`, `school_memberships`, `coach_athlete_assignments`, `coach_group_assignments` | `src/modules/accounts`, `src/modules/school-console` |
| Consent records: purpose, text version, acceptance and withdrawal time | Guardian or adult athlete, per athlete | `authorizations`, `authorization_texts` (`20261025010000_accounts_authorizations_invitations.sql`) | `src/modules/accounts` |
| Race and training times with stroke, distance, pool, session type, capture time and source | Athlete | `measurements`, `timing_series` (`20261024220000_timing_measurements.sql`) | `src/modules/timing` |
| Device identifier generated by the app, stored with each time and plan mark | Device | `measurements.device_id`, `timing_series.device_id`, `training_plan_fulfillments.device_id` | `src/modules/timing`, `src/modules/training-plans` |
| Training plans assigned to an athlete, group or school, and the mark of whether each session was done | Athlete | `training_plans`, `training_plan_versions`, `training_plan_blocks`, `training_plan_assignments`, `training_plan_fulfillments` | `src/modules/training-plans` |
| Free-text note (up to 500 characters) from a guardian or adult athlete on a session | Athlete | `training_plan_notices.body` (`20261026070000_training-plans_notices.sql`) | `src/modules/training-plans` |
| Official results imported for an athlete, with provenance, and the confirmation of "Is this person?" | Athlete | `imported_results`, `results_import_confirmations`, `results_import_pending`, `results_import_queries` (`20261028233000_results-import_provenance.sql`, `20261029220000_results-import_pending.sql`; the query window is per athlete and provider since `20261112120000_results-import_platform_per_provider.sql`) | `src/modules/results-import` |
| Pilot invitation token | Invited family | `school_invitations.token` | `src/modules/accounts` |

Local copy: `src/core/sync` keeps the rows a user may read in an **encrypted** on-device database (SQLCipher, `ENCRYPTED_DB_FILENAME`; the key is generated on the device and kept with `expo-secure-store`, see `src/core/sync/databaseKey.ts` and `db.ts`) so the app works offline. `powersync/sync-config.yaml` limits each device to the rows its signed-in user could read online.

## Proposed answers

### Data collection and security

| Question | Proposed answer | Reason |
| --- | --- | --- |
| Does the app collect or share any of the required user data types? | Yes | See below. |
| Is all of the user data collected by your app encrypted in transit? | Yes | Both production URLs (API and PowerSync) are `https://`, behind Cloudflare; confirmed by the maintainer. The app itself reads them from build variables (`src/core/sync/supabase.ts`) and does not enforce a scheme, so re-check them if either URL changes. |
| Do you provide a way for users to request that their data is deleted? | **Open decision** | No in-app account or data deletion flow exists in `src/` today; only the withdrawal of an authorization does (`authorizations.withdrawn_at`). Play also asks apps that create accounts for a deletion path in the app and on the web: the maintainer decides whether to offer a request by email (stated in the privacy policy) or to build it, before the closed test. |

### Data types

For each type: collected, shared, processed ephemerally, required or optional, and purposes. "Shared" follows Play's definition: transferring user data to a third party. Handing data to a service provider that processes it on the developer's behalf (hosting, email delivery) is **not** sharing in Play's definition; confirm each provider against that definition.

| Play category and type | Collected | Shared | Required | Purposes | Basis |
| --- | --- | --- | --- | --- | --- |
| Personal info: Name | Yes | **Yes**, only to the official results source when the user imports official results with the authorization granted | Required to collect; the sharing is optional | App functionality, account management | `adult_profiles`, `athletes`; sharing in `supabase/functions/results-import` |
| Personal info: Email address | Yes | No | Required | App functionality, account management | Auth sign-in with an emailed code |
| Personal info: User IDs | Yes | No | Required | App functionality, account management | `auth.users.id` |
| Personal info: Other info (athlete identity document number) | Yes | **Yes**, only to the official results source when the user imports official results with the authorization granted (same condition as the name) | Optional (the field is labelled optional in `src/modules/accounts/i18n/es-CO.json`; it is needed to import official results) | App functionality | `athlete_identity_documents`, encrypted at rest; sent by `refreshResults` → `provider.fetchResults(identityNumber)` |
| Health and fitness: Fitness info (swim times, training plans, completed sessions) | Yes | No | Required for the timing and plan features | App functionality | `measurements`, `training_plan_*` |
| Messages: Other in-app messages (notes on a session) | Yes | No | Optional | App functionality | `training_plan_notices` |
| Device or other IDs (app-generated device identifier) | Yes | No | Required | App functionality (tells apart records captured on different devices to solve conflicts) | `measurements.device_id` and `measurement_conflicts` |

Play types **not** collected, according to the code: location, financial info, health info other than fitness, contacts, photos and videos, audio, files and documents, calendar, web browsing, installed apps, app interactions, crash logs, diagnostics, and advertising ID.

### Sharing to review with the maintainer and the legal review

1. **Official results import.** When a guardian or adult athlete uses "Import official results", the server function `supabase/functions/results-import` sends the athlete's first and last name, and the stored identity document number (read back decrypted for the call: `refreshResults` → `provider.fetchResults(identityNumber)`), to the official results source of the organization that is chosen, through the provider adapter `<country>-<organization>` (ADR 0003). That is a transfer of personal data to a third party. It happens only with the `import_official_results` authorization granted by the guardian or the adult athlete (`authorization_purposes`). Proposed answer, confirmed by the maintainer for the identity number and applied to the name too: **shared = Yes, optional, purpose App functionality**, with the same authorization condition. A results platform adapter (`TournamentProvider`, for example `co-colombiaacuatica`, not registered yet) works differently: the person pastes one tournament address, the server downloads that tournament's public LENEX results file and searches it for the identity number (the stored one, or the one typed) on the server, so the number is not sent to the platform. The legal review may refine how the source is described.
2. **Email delivery.** The auth server sends the sign-in code through an SMTP provider. Treated as a service provider, not sharing. Confirm the provider and its terms.
3. **Third-party sign-in.** Google sign-in is enabled in production (verified by the maintainer in the auth logs: authorize → provider → callback), and the sign-in screen has a Microsoft button too (`src/modules/accounts/components/ProviderOptions.tsx`). Whether Microsoft sign-in works in production is **to be confirmed by Mario**; this draft states neither that it is enabled nor that it is not. With a provider, the email address (and the name, if the provider returns it) comes from that provider through Supabase Auth. It is the same Email and Name already declared above; signing in through a provider is not sharing to a third party.
4. **Sharing inside the platform.** A school can read the times of its own athletes, and a guardian can authorize sharing results with a school (`school_result_sharing`, `share_results_with_school`). That is between users of the same app, enforced by row-level security, not a transfer to a third party.

## Open questions

- Does Play treat minors' data held on behalf of a guardian as "data of children"? Depends on the target audience declaration in [`docs/RELEASING.md`](../RELEASING.md#open-decisions).
- Retention: no deletion or expiry rule exists for `measurements`, `authorizations`, or `athletes` today. `results_import_pending.expires_at` is the only expiry in the schema.
- Backups of the server database are out of scope of this draft; they belong to the privacy policy once the hosting decision (ADR 0002) fixes where they live.
