## What the app collects

Everything is entered by the user or captured by the timing screens. There is no advertising, analytics, or crash-reporting SDK in `package.json`, no location or contacts permission, and no code that reads the device advertising ID. The individual stopwatch can record video with the camera and the microphone and saves it to the phone's gallery (#1088, merged in #1138): see [Video from the individual stopwatch](#video-from-the-individual-stopwatch). The camera is also used to scan the QR of a swimmer's share code (#1322): see [Scanning the swimmer's code QR](#scanning-the-swimmers-code-qr). **PENDIENTE de revisión legal:** every text about video, camera, microphone and gallery storage in this document.

Local copy: `src/core/sync` keeps the rows a user may read in an **encrypted** on-device database (SQLCipher, `ENCRYPTED_DB_FILENAME`; the key is generated on the device and kept with `expo-secure-store`, see `src/core/sync/databaseKey.ts` and `db.ts`) so the app works offline. `powersync/sync-config.yaml` limits each device to the rows its signed-in user could read online.

Videos recorded with the individual stopwatch are not in this database or in the sync: they stay in the phone's gallery (see [Video from the individual stopwatch](#video-from-the-individual-stopwatch)).

A guardian's device receives only the school times the school shares with that guardian (`measurements.guardian_visible`) and the rows hidden after an authorization withdrawal; when sharing is switched off, the stream stops matching those rows and the device drops them on its next sync. An adult athlete's device receives all their own.

A coach whose membership is deactivated stops receiving the data of that school: the streams drop the school's athletes, results, plans and assignments, and only the coach's own membership row (with its deactivation time) keeps syncing so the app can show it. In a local run (PowerSync service 1.21.0, `@powersync/node` 1.2.0, one row of each kind in the school) the device of a connected coach went from 1 to 0 rows of that school in `athletes`, `measurements`, `training_plans` and `schools` about half a second after the deactivation, and a device that was offline kept all of them until it reconnected and dropped them on that first sync. SQLite does not erase the freed space of deleted rows, so bytes of them can stay in the database file until it is overwritten; in the app that file is encrypted.
A device that never connects again keeps its encrypted copy until it does. The deactivated coach's uploads still waiting on the device keep being rejected with `42501` into `upload_failures` and do not block the queue.

Two answers and one code kept on the phone (the answers so the app opens without waiting for the server, issue 1311). All three are in `expo-secure-store` (the Android Keystore, encrypted), never in a table, never synced and never uploaded. The first two each hold only the own user ID and one answer about the signed-in account: (1) `trailskill-deletion-status`: whether the account is marked for deletion, with the deletion date when it is (`src/modules/accounts/data/knownDeletionStatus.ts`); (2) `trailskill-platform-admin`: a boolean, whether the account is a platform administrator (`src/modules/timing/data/knownPlatformAdmin.ts`). The app opens from them and asks the server again in the background; a changed answer replaces the stored one at once (a marked account is blocked, and the landing is chosen again). An unknown answer reads as «not a platform admin» and as «not marked» only when nothing was ever known; the server still decides what each account may do. A value stored for another user ID is ignored. Both answers are deleted when the session ends (`useKnownDeletionStatusGuard`, `useKnownPlatformAdminGuard`, mounted in `src/app/_layout.tsx`); they leave with the app's data when it is uninstalled. The third entry is (3) `trailskill-recovery-code.<user ID>.<swimmer ID>` (plus `trailskill-recovery-confirm.<user ID>.<swimmer ID>` while the server has not been told that the code was saved): the permanent code of a swimmer (#1416, `src/modules/athletes/data/recoveryCodeVault.ts`). The server never knows its text, so if it is lost nobody can read it again; for that reason it is **kept** when the session ends and after the account or the swimmer is erased: the app removes it only when the server no longer honours that code (its set was replaced). It leaves with the app's data when it is uninstalled. The single-use recovery codes are never saved on the phone. **PENDIENTE de revisión legal.** In development builds only, a log line lists the milliseconds of each start step (`src/core/startup`), with no ID, email, name or path.

## Proposed answers

### Target audience and roles

Decided by the maintainer on 2026-11-22 ([`docs/product/swimmer-data-lifecycle.md`](../product/swimmer-data-lifecycle.md), issue #1415); **PENDIENTE de revisión legal** (#106).

- **Target audience: 18+.** The people who use the app are adults: guardians, adult athletes, coaches and school administrators. A minor never signs in; the data of minors is registered and authorized by their guardian. Answer «18 and over» only in the target audience declaration, and re-check with the legal review whether Play's Families Policy still applies because the app stores minors' data.
- **Who owns and who answers for the data.** The family owns a swimmer's data. The school is the controller (Responsable) of what it collects while the swimmer is enrolled and for 30 days after the baja, with Swimcro as its processor (Encargado) under a transmission contract ([`transmission-contract.es.md`](transmission-contract.es.md), Decreto 1377 de 2013, art. 25). Swimcro is the controller of independent use (registration without a school, «Mis tiempos», times sent between families). For the form, a school reading a swimmer's data is the same in-platform sharing as before; nothing new is collected by this change.
- **What stays the same in the form.** This change adds no data type and no sync stream. The 30-day reading window (#1418), the transfer to a new school (#1419) and the school's copy are enforced in `main`. The school's copy is **pseudonymized, not anonymous** (#1420; see the note on #106): it carries no identity and no key the school can see; the server links it to the original swimmer while that swimmer exists (`source_athlete_id`) and, if the owner already issued the permanent code, to that code's recovery identity (a copy made before any code exists gets that link when the owner issues the code, while the swimmer exists). A school can make the copy while the swimmer is still enrolled, and the copy has no end date. Whoever holds the permanent code or a recovery code can ask for it, but receives it only if the school's admin approves, and only when the code belongs to an erased swimmer, to one nobody manages or to one the caller already manages. A school that joined through an invitation the family accepted also reads the history of the schools whose link already ended (#1419, `athlete_history_grants`), read-only and online. Re-check the rows above in the pull request that shows these rules in the app.

### Athlete photo

Issue #1221, PR 2 of 4 (data model, access rule and sync; the upload screen, the offline queue and the Data safety permissions table are PR 3, the avatar on screens is PR 4). **PENDIENTE de revisión legal** for every sentence. What the code does:

1. **Where it is stored.** An object per upload in the private bucket `athlete-photos` (`<athlete_id>/<uuid>.jpg`, a new path on every change) and one row per athlete in `athlete_photos` that names the current object. No public URL exists. Evidence: `supabase/migrations/20261119150500_athletes_photos.sql`.
2. **Who reads it.** Only someone who can already see the athlete (guardian or adult athlete, coach through a group or direct assignment, school admin: `app.visible_athlete_ids()`) and only while the `show_photo` authorization is in force (`authorization_status.is_granted`). The same function guards the row (`athlete_photos_select`) and the object (`athlete_photos_objects_select` on `storage.objects`); Storage signs a URL only for an object the caller can select. Platform admins are not included. Tests: `supabase/tests/database/athletes/photos.test.sql`.
3. **Who writes it.** Only a guardian of the athlete or the adult athlete themselves. Inserting or replacing needs `show_photo` in force; deleting the row and the object does not, and the same people read the current photo after a withdrawal only to delete it (#1234). A coach or a school admin cannot insert, change or delete the row or the object.
4. **Sync.** The stream `athletes_photos` (`powersync/sync-config.yaml`) gives the row to the same people under the same condition, so withdrawing `show_photo` removes the row from every device on its next sync. The image is never synced.
5. **On the phone.** `useAthletePhoto` copies the image to the app's private cache (`cacheDirectory/athlete-photos/<athlete_id>/`), without encryption, and empties it on sign-out and when `show_photo` stops being in force. Nothing logs a path, a URL or a file URI.
6. **Taking the photo (issue #1222).** The person chooses the camera or the system Photo Picker, crops it square, and the app re-encodes it as a 512 px JPEG at quality 0.8 (`expo-image-manipulator`); the re-encoding drops the EXIF block (location, device, time). Only a guardian of the athlete or the adult athlete themselves sees the buttons, and only while `show_photo` is in force; without it the button opens the authorization flow first. A coach never sees them.
7. **Waiting for the connection.** The image waits on the phone in `documentDirectory/athlete-photo-uploads/<athlete id>/`, **not encrypted**, named by one row of the local-only table `athlete_photo_uploads` (`athlete_id`, `local_uri`; it never syncs). When there is signal the object goes up as `<athlete id>/<uuid>.jpg` and only then is the `athlete_photos` row written; then the queue row and the file are deleted. A photo the server refuses for good (policy, size, type) is dropped with its file. The queue and its files are deleted when the session ends and, for one athlete, when `show_photo` is withdrawn. The picker's own copy (`cacheDirectory/ImagePicker/`, full size) is deleted as soon as the 512 px JPEG exists; after the upload the JPEG moves into the photo cache of point 5 so it keeps showing until the row reaches the server. Nothing logs a path, a URL or a file URI.
8. **Taking it away.** «Quitar foto» in the profile, and the offer shown right after withdrawing `show_photo`, delete the **object first and the row after it**; they need signal. If the object cannot be deleted the row stays. Deleting a replaced photo's old object is the server's cleanup queue (#1232, #1233), not the app.
9. **Accepted limits (decided on the issue, to confirm in the legal review).** A signed URL already handed out stays valid for about 5 minutes after a withdrawal. Storage only serves the object the row points to. When a photo row is deleted, replaced, or removed with its athlete (cascade), its old path goes to the private table `storage_deletion_queue`; the client deletes the object through the Storage API when it can, and the daily account deletion worker drains the queue (#1233). Until the object is deleted it stays in Storage, unreadable by app users. A request to delete the data by email (privacy policy, section 11) includes the photo. Also: a queued photo is lost if the person signs out before it goes up (the unsent-records warning counts only synced tables); a row that syncs before the object finishes uploading falls back to the initials; and if the sync has already taken the row off the device when the person accepts the offer to delete after a withdrawal, the object is deleted but the server row, which the device no longer holds, is not deleted by the app.

### Birth date and gender of an athlete

1. **Where it is stored.** One row per athlete in `athlete_private_details` (`birth_date`, `gender`), both nullable. The server checks the values: the birth date is between 1900-01-01 and the server date, and the gender is `F`, `M` or `undisclosed`.
2. **Who reads and writes it.** Only whoever manages the athlete (`app.managed_athlete_ids()`: a guardian, or the adult athlete themselves) and a platform admin. A coach, a school admin, another guardian and a stranger read and write nothing. The school console never shows the birth date.
3. **Sync.** The stream `athletes_private_details` gives the row only to the people who manage the athlete. `athletes_visible`, which coaches and school admins also receive, does not carry the two columns.
4. **Deletion.** `erase_account` deletes the row with the rest of the athlete, also when the athlete stays as a pseudonymized placeholder.
5. **Pending.** Legal review of how a minor's birth date is processed (#106); the screen that asks for it is issue #1367.

### Account deletion

Built by #1244 (server only; screens in #1245, review in #106). What a person can verify:

1. **Request and code.** `request` sends a 6-digit code to the account email through Resend. The code is valid 10 minutes, allows 5 attempts (the 6th fails even with the right code) and is stored only as a salted hash in `account_deletion_codes`; sends are counted per account in the database (`account_deletion_code_sends`, provisional limit to confirm by the maintainer).
2. **School rule.** `request`, `confirm` and the SQL functions refuse, without marking anything, when the user or a swimmer they manage is still active in a school (`athlete_schools.ended_at is null`), or when the user has an active coach or school admin membership, or is a platform admin. The answer names the school.
3. **Grace period.** `confirm` creates a row in `account_deletion_requests` with `delete_after` = now + 30 days. The row holds the account email until the last email leaves and is deleted with it; no other table keeps it. While the row is `pending` the account is blocked: its writes are refused by database triggers and its data stops syncing (`powersync/sync-config.yaml`). A guardian who co-administers a swimmer keeps their own access. `cancel` removes the row.
4. **Day 30.** A daily `pg_cron` job calls the `accounts-deletion-worker` function through `pg_net`; the worker calls `public.erase_account` once per due request, in one transaction. It deletes the account (`auth.users`), profile, «Mis tiempos», transfers, share codes and the authorizations the user gave; each swimmer whose only manager is the user, with their data; and only the user's link to a swimmer another guardian also manages. Photo files are queued in `storage_deletion_queue`; the same daily run drains it (#1233), and only the Storage API deletes files. Orphan photo objects (no photo row, older than 24 h) are deleted by the same run once the maintainer sets `STORAGE_ORPHAN_SWEEP=delete`; until then it only counts them.
5. **School times are kept, pseudonymized.** A deleted swimmer that has school-recorded times stays as a placeholder without name, document, photo, birth date or gender, and the privacy policy says so with «…y sus vínculos con acudientes, grupos y entrenadores; sus vínculos con escuelas, que ya terminaron antes del borrado, se conservan sin datos que lo identifiquen.» `erase_account` does not end or select school links: the placeholder keeps its school links (`athlete_schools`) as they were, all already ended because the deletion is refused, at the request and again on the day (`app.account_deletion_blockers`), while the user manages a swimmer with an active link. What stays besides those links: the history permissions of a transfer (`athlete_history_grants`) and the rows of the owner's sharing with a school (`athlete_result_sharing`), which cascade with the swimmer and so are kept with the placeholder. It has a random `former_athlete_key` of which the server keeps only the SHA-256 hash (`former_athlete_keys.key_hash`). The plain key travels only in the confirmation email (it waits in the request row until that email leaves, like the address).
6. **Audit.** One row in `account_deletion_audit`: random id, time, roles and counts only.
7. **Emails (Resend).** On marking (date and how to cancel), reminder on day 23, confirmation after the deletion, and a notice when a school linked the swimmer again and the deletion was stopped.
8. **Limits.** Files already in Storage stay until the next daily run drains the queue (#1233; unreadable by app users meanwhile). Videos of the stopwatch are on the phone and are not touched.

### Relinking the school times of an erased swimmer

Built by #1251 (migration `20261122100000_athletes_relink_requests.sql`; screens in the same issue). A family that comes back can ask the school to give the times it kept for an erased swimmer (account deletion, step 5) to the swimmer they manage today. What a person can verify:

1. **Key.** The family types the `former_athlete_key` from the deletion email. `request_athlete_relink` compares its SHA-256 hash with `former_athlete_keys.key_hash` on the server. The key is never stored: not in `athlete_relink_requests` (which has no column for it, not even its hash), not in `athlete_relink_attempts`, not in a log.
2. **Wrong keys.** A wrong or malformed key creates no request and gets the same answer whether or not a marker exists (`invalid_key`). Each wrong key is recorded without its text in `athlete_relink_attempts`; past a limit per signed-in user and per swimmer in 24 hours (provisional values in the function, to confirm by the maintainer) the function answers `rate_limited` and checks nothing.
3. **Who decides.** One request per school that owns times of the marker. Only an active `school_admin` of that school (membership without `deactivated_at`) reads its inbox, approves or rejects; a coach, an admin of another school, a deactivated admin and the family are refused. The admin sees the first and last name of the swimmer the family asks for, even if the swimmer is not in the school; nothing else about the family.
4. **Approval.** In one transaction, with the request row locked (two approvals at once move the times once), the times of that school on the marker move to the swimmer of the family. The marker stays, empty. The moved times take the sharing setting of the new swimmer-and-school pair (the school's default when the pair has no switch), so the guardian sees them only if the school shares them; the approval does not link the swimmer to the school, so the school's staff read them only while there is an active link. Rejecting moves nothing. The rows are closed with the decision, the time, the deciding user (no foreign key: erase_account empties nothing here) and how many times moved.
5. **Storage.** Both tables have row level security with no policy and no grant, are not in the PowerSync publication and are guarded against writes of an account marked for deletion. The screens need a connection and keep nothing on the phone. A request goes with the account of the family that made it (`on delete cascade`).
6. **Limits.** The deciding user stays in the closed request until a retention period is defined by the legal review (#106).

### Sharing to review with the maintainer and the legal review

1. **Official results import.** When a guardian or adult athlete uses "Import official results", the server function `supabase/functions/results-import` sends the athlete's first and last name, and the stored identity document number (read back decrypted for the call: `refreshResults` → `provider.fetchResults(identityNumber)`), to the official results source of the organization that is chosen, through the provider adapter `<country>-<organization>` (ADR 0003). That is a transfer of personal data to a third party. It happens only with the `import_official_results` authorization granted by the guardian or the adult athlete (`authorization_purposes`). Proposed answer, confirmed by the maintainer for the identity number and applied to the name too: **shared = Yes, optional, purpose App functionality**, with the same authorization condition. A results platform adapter (`TournamentProvider`, for example `co-colombiaacuatica`, not registered yet) works differently: the person pastes one tournament address, the server downloads that tournament's public LENEX results file and searches it for the identity number (the stored one, or the one typed) on the server, so the number is not sent to the platform. When a tournament has no LENEX file, the server downloads its public results PDF instead (a plain GET of an address built from the tournament's own date, which carries nothing about the athlete) and searches it on the server by the athlete's name and birth date (read from the database after the same authorization check, issue #1482), so neither is sent to the platform; the name and birth date that the PDF shows of other swimmers are never kept or returned. The legal review may refine how the source is described.
2. **Email delivery.** The auth server sends the sign-in code through Resend, an email delivery provider: **confirmed by the maintainer on 2026-11-15; this repository does not show it** (the SMTP host is a redacted variable of the Supabase stack in Dokploy). It receives the recipient address and the code. Treated as a service provider, not sharing. Confirm the provider's terms and where it processes the data. The coach invitation is also sent by email through Resend, the same provider (`supabase/functions/school-console-invite-coach/resendSender.ts`, issue #1046): it receives the invited coach's email address (the recipient) and the school's name (in the subject and the text); the message carries no other data and no link. Without `RESEND_API_KEY` the function sends nothing and only records the invitation (`testSender.ts`, development and tests). Also a service provider, not sharing. The family invitation is not sent by email: it is a link the admin shares by hand **(review 2026-11-16)**.
3. **Third-party sign-in.** Google sign-in is enabled in production (verified by the maintainer in the auth logs: authorize → provider → callback), and the sign-in screen has a Microsoft button too (`src/modules/accounts/components/ProviderOptions.tsx`). Whether Microsoft sign-in works in production is **to be confirmed by Mario**; this draft states neither that it is enabled nor that it is not. With a provider, the email address (and the name, if the provider returns it) comes from that provider through Supabase Auth. It is the same Email and Name already declared above; signing in through a provider is not sharing to a third party.
4. **Sharing inside the platform.** A school can read the times of its own athletes, and a guardian can authorize sharing results with a school (`school_result_sharing`, `share_results_with_school`). When a family joins a school with an invitation, it accepts the three purposes of data and times together (recording times, importing official results and sharing results with another school), with the full text and version shown and kept as evidence; the photo stays a separate optional authorization, and each purpose is withdrawn one by one (decision of the maintainer, 2026-11-21, issue #1328). That is between users of the same app, enforced by row-level security, not a transfer to a third party.
5. **Share code of an athlete.** Who manages an athlete can give the athlete's code to another family, so that family can send times measured for the athlete (issue #972; the request and its acceptance are #973). Looking a code up shows only the athlete's short name (first name and the initial of the last name, "Ana M.") to the user who typed it; nothing else about the athlete. Giving the code and accepting the request is the consent (rule decided by the maintainer on 14 Nov 2026), and the code can be changed at any time, which stops the old one at once. Sending a time (#973): the receiving family sees the time as it was sent, never the sender's other times; the sender sees only the short name and whether the request is still waiting. Accepted, the time becomes the receiving family's and leaves the sender's list. Between users of the same app, not a transfer to a third party. Once a family accepted a time sent with their code, the sender keeps that code and the swimmer's short name for the next sends (`saved_athlete_share_codes`, #1302; the user reads only their own rows and removes one with «Quitar»). When the family changes the code, the kept code is not deleted: it stays marked as expired (`expired_at`, #1320) until the user sends with the new code, removes it, or the family removes the code or the swimmer, so the user sees that it expired and asks for it again. Kept codes are deleted with the account like the rest of the user's data.

6. **Video.** The app does not send it to any third party. The person can share it with «Compartir video» through Android's share menu, choosing the app and the recipient (#1201; see [Video from the individual stopwatch](#video-from-the-individual-stopwatch)); that transfer is started by the person, and the video may show other minors (a notice before sharing was left out of this phase by the product owner). **PENDIENTE de revisión legal:** whether this changes the Play form's answer. An app on the phone that the person allows to read photos and videos can read the gallery album; that is the phone's own permission system, not a transfer by Swimcro. **PENDIENTE de revisión legal.**
